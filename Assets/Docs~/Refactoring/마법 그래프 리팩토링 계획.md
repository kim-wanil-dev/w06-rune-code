# 마법 그래프 리팩토링 계획

> 기준 문서: 같은 폴더의 「마법 그래프 구현 규칙.md」(이하 **규칙**). 규칙과 기존 구현이 다르면 규칙을 따른다.
> 작업 규칙: 저장소 루트의 `AGENTS.md`. Git 명령 금지, 테스트 코드·테스트 자산 추가 금지.
> 상태: **계획 단계. 구현은 시작하지 않았다.** 0단계의 결정 표를 확정한 뒤 1단계부터 진행한다.

## 1. 목표와 범위

### 1.1 무엇이 바뀌는가

| 구분 | 현재 시스템 | 리팩토링 후 (규칙) |
|---|---|---|
| 실행 모델 | 그래프를 시전 전에 **실행 트리(`SpellAction`)로 컴파일**하고, 시전하면 트리를 즉시 펼쳐 실행 | 그래프는 읽기 전용으로 두고, 시전하면 **토큰**이 흐름선을 따라 실시간으로 노드를 지난다 |
| 비용 | 컴파일 때 최악 비용을 계산해 시전 시 한 번에 선지불 | 마나풀에서 적재량만 빼고, 토큰이 **노드에 도착할 때마다** 그때의 값으로 비용을 지불 |
| 노드 | 룬 21종(형태 4, 속성 3, 수식 8, 흐름 3, 행동 2, Core) | 9종: 시전, 투사체, 증폭, 가산, 분열, 분배, 합류, 분기, 적중 |
| 포트 | `exec`/`mod` 두 종류, 입력 1개 제한, 출력 팬아웃 무제한 | 흐름 포트만 있음. **출력 1개당 엣지 1개**, 입력은 여러 개, 역방향·자기 연결(루프) 허용 |
| 검증 | E1~E10, W1~W4, RAM 용량, 해금, 순환 금지 | 시전 1개, 적중 0~1개, 시전·적중에 입력 없음. 도달 불가 노드는 회색, 투사체가 없으면 경고만 |
| 투사체 | 볼트·버스트·오비트·존, 관통·유도·속성 | 직선 투사체 하나. 관통 없음, 적중하면 적중 노드에서 새 토큰 |
| 피해 | 적응·속성·상태이상·이지스·릴레이 파이프라인 | `실피해 = max(0, 위력 − 경감)` |
| 시전 입력 | 미션에서는 포인터가 전투 영역에 있으면 연속 시전 | 누를 때마다 한 번 시도. 누르고 있어도 반복하지 않음 |
| 표시 | 실행된 노드를 0.2초 하이라이트 | 토큰 수·마지막 지불 비용·소멸 표시를 보여 주는 **그래프 오버레이** |

### 1.2 유지하는 것

- 폴더 구조, 어셈블리 경계(`RuneCode.Core` → Game/UI/Save 단방향), 60Hz 고정 틱, `double` 연산, mulberry32 RNG, `StateHash` 기반 회귀 확인.
- 화면 흐름(타이틀 → 작업실 → 출격 → 결과), 시간제 전투, 적 이동·공격·유입·보스 패턴, 조각 정산.
- 편집기 조작(팔레트 배치, 드래그 이동, 박스 선택, 우클릭 엣지 삭제, Undo/Redo, 복사·붙여넣기, 줌·팬).
- `SpellGraph`/`GraphNode`/`GraphEdge`/`NodeParameter`의 **직렬화 필드 이름과 타입**(3.2절). 저장·복제·Undo가 같은 경로를 계속 쓴다.

### 1.3 범위 밖 (규칙 13절)

센서·데이터선, 이동·조준 노드, 추가 조준 모드, 노드 획득·파밍, 다중 슬롯, 속성 상성, 빔·장판, 실행 로그·느린 재생, 그래프 공유(RC1), 적 AI·생성·웨이브 변경.

## 3. 목표 구조

### 3.1 계층

```
Core/Data        BalanceData(+ SpellSettings 섹션) · EnemyCatalog(+ 경감) · GameData
Core/Graph       SpellGraph(스키마 유지) · SpellNodes(노드 종류 표) · SpellProgram(읽기 전용 실행 그래프) · ShareCodec(직렬화만)
Core/Simulation  SpellRuntime(토큰·발사 요청·투사체) · SpellRuntimeTypes · RuneSimulation(틱 순서 통합) · SimulationTypes
Game/UI          RuneCodeApp(편집 연산·입력) · RuneGraphCanvas(편집 + 실시간 흐름) · RuneGraphOverlay(전투 오버레이) · GraphLayout(공용 배치)
```

제거 대상: `GraphCompiler`, `CompiledSpell`(`SpellAction`·`SpellStats`·`SpellCondition`·`CompileIssue`·`CompileResult`), `RuneData.cs`와 `runes.json`, `spells/*.json`, `AdaptationNet`(D2), `SimulationSpellEntity`, 예약 실행 큐, RC1 인코딩(D4).

### 3.2 그래프 데이터 (스키마 유지, 값만 바뀜)

기존 직렬화 필드를 그대로 쓴다. 저장·복제·Undo·변경 비교 경로를 다시 만들 필요가 없다.

| 필드 | 새 의미 | 예 |
|---|---|---|
| `GraphNode._runeId` | 노드 종류 ID | `cast`, `projectile`, `amplify`, `add`, `split`, `fork`, `join`, `branch`, `onHit` |
| `GraphNode._params` | 노드 파라미터 | 시전 `aim`(text: `cursor`/`nearest`), `load`(number) · 증폭 `ratio` · 분배 `share`(10~90) · 분기 `condition`(text), `compare`(text: `ge`/`le`), `threshold`(number) |
| `GraphNode._x`, `_y` | 편집기 좌표. **규칙에 쓰지 않는다** | |
| `GraphEdge._fromPort`, `_toPort` | 포트 번호의 문자열 | `"0"`, `"1"` |

- 포트 번호 문자열은 `ShareCodec.IsIdentifier`를 통과한다.
- 프로퍼티 이름 `RuneId`는 호출부를 줄이기 위해 유지하고, `SpellNodes.TryParse`로 종류 enum을 얻는다.
- `SpellGraph.Create`는 기본 그래프 `시전(core) → 투사체`를 만든다.

### 3.3 노드 종류 표 (`Core/Graph/SpellNodes.cs`)

- `enum SpellNodeKind`과, 종류별 ID 문자열·입력/출력 포트 수·머무는 시간·파라미터 키를 가진 정적 표.
- 포트 수는 규칙 5.1이 정하므로 코드 상수다. 숫자 값(비용 계수, 머무는 시간, 파라미터 범위)은 모두 `SpellSettings`에서 읽는다.
- 비용 계산 `Cost(kind, token, node, settings)`를 한곳에 둔다. 비용 바닥값 1(시전·적중 제외)도 여기서 보장한다.
- 편집기의 비용 공식 문구(예: `위력×(2.0−1)×0.4`)도 같은 표에서 만든다(규칙 9절).

### 3.4 실행 그래프 (`Core/Graph/SpellProgram.cs`)

`SpellGraph`에서 한 번 만들어 시뮬레이션에 넘기는 **읽기 전용 색인 구조**다. 토큰마다 그래프를 복제하지 않는다(규칙 1절).

- 노드를 0..N−1 정수 색인으로 바꾸고 `nodeId ↔ index` 표를 가진다.
- `Next[node, outPort] → (targetNode, inPort)` 또는 없음. 출력 포트당 엣지가 1개이므로 O(1)로 찾는다.
- 파라미터는 기본값까지 반영한 숫자로 미리 풀어 둔다.
- 검증 결과도 함께 만든다: 구조 오류(시전 ≠ 1, 적중 > 1, 시전·적중으로 들어오는 엣지, 같은 출력 포트의 중복 엣지, 알 수 없는 종류·포트), 도달 가능 집합(시전 또는 적중에서 출발), 경고(시전에서 도달 가능한 투사체 없음).
- 구조 오류가 있으면 프로그램을 만들지 않는다. 편집기는 오류를 표시하고 출격·시험 시전을 막는다. 편집 연산이 구조 오류를 만들지 않으므로, 이 오류는 손상된 저장에서만 나와야 한다.

### 3.5 런타임 (`Core/Simulation/SpellRuntime.cs`, `SpellRuntimeTypes.cs`)

| 타입 | 내용 |
|---|---|
| `SpellToken` | 규칙 2.2의 필드 전부. 통과 횟수는 노드 색인 배열이나 사전으로 둔다. 변경자는 `internal` |
| `SpellProjectile` | 규칙 2.3. 위력, 운반 마나, 세대, 무시할 적, 시전 id, 위치, 방향, 이동 거리 |
| `FireRequest` | 토큰 id, 개수, 위력, 운반 마나, 세대, 무시할 적, 시전 id, 원점(캐릭터 또는 지점과 방향) |
| `TokenEndEvent` | 노드 색인, 사유(지불 불가 / 수명 초과), 필요 비용, 보유 마나, 틱. 표시용 |
| `NodeFeedback` | 노드별 마지막 지불 비용과 틱. 표시용 |
| `CastResult` | 성공 / 마나 부족 / 과부하 |

`SpellRuntime`은 토큰 목록, 합류 대기열(노드·포트별 FIFO), 이번 프레임의 발사 요청, 투사체 목록을 가진다. 외부에는 읽기 전용 목록만 공개한다. 공개 메서드는 아래와 같다.

- `TryCast(...)`: 시전(4.1)
- `ProcessTokens(dt)`: 토큰 처리(4.3, 4.4, 5.2)
- `FlushFireRequests(...)`: 발사 요청 묶기(6.1)
- `AdvanceProjectiles(...)`: 투사체 비행·충돌·적중 토큰(6.2, 6.3)
- `Clear()`: 실행 상태 전부 삭제(9절)

적·맵·플레이어는 `RuneSimulation`이 인자로 넘긴다. 단순 기능이므로 인터페이스나 추상 계층을 추가하지 않는다.

### 3.6 틱 순서 (`RuneSimulation.Step`)

규칙 4.2를 기존 틱에 끼운다. 바뀌는 줄만 적는다.

```
 1  Player.Advance           ← 마나풀 회복(설정값 + D1 성장분). 쿨다운은 제거
 2  MovePlayer, 적 유입      (기존)
 3  시전 입력이 이번 틱에 눌렸으면 SpellRuntime.TryCast    ← 새 토큰은 6에서 같은 틱에 처리
 4  AdvanceStatuses 제거(D2), AdvanceEnemies, RunEnemyShots (기존)
 5  SpellRuntime.AdvanceProjectiles  ← 규칙 4.2-2. 적중 토큰은 목록에 넣기만 하고 다음 틱부터 처리
 6  SpellRuntime.ProcessTokens       ← 규칙 4.2-3. 생성 순서대로
 7  SpellRuntime.FlushFireRequests   ← 규칙 4.2-4. 새 투사체는 다음 틱부터 이동
 8  적 탄환, 사망 적 정리, 오브, 종료 판정, _tick++ (기존)
```

`RunScheduled`, `AdvanceSpellEntities`, 적응 갱신은 삭제한다. `StateHash`에는 토큰, 합류 대기, 투사체, 노드 피드백을 생성 순서대로 기록하고 로드아웃 서명은 그래프 서명으로 바꾼다.

### 3.7 구현 해석 (규칙이 열어 둔 세부)

구현자가 임의로 정하지 않도록 고정한다. 바꾸려면 0단계 결정과 같은 절차를 밟는다.

| ID | 항목 | 해석 |
|---|---|---|
| I1 | 시전 토큰의 첫 처리 시점 | 시전한 틱의 6번에서 처리한다. 남은 대기 시간이 시전 노드의 머무는 시간 0.05이므로 3틱째에 첫 노드로 간다 |
| I2 | 적중 토큰을 다음 틱부터 처리 | 토큰에 생성 틱을 기록하고, 6번에서 생성 틱이 현재 틱인 적중 토큰은 건너뛴다 |
| I3 | 분배 복제 토큰 | 목록 끝에 추가하되, 원본 처리가 끝난 직후 같은 틱에 [진행 루프]부터 처리한다. 복제가 다시 분배하면 같은 방식으로 이어서 처리한다. 다음 틱부터는 목록 순서(생성 순서)대로 처리한다 |
| I4 | 합류에서 흡수 | 흡수하는 토큰은 필드만 바꾼다(대기 해제, 남은 대기 0.05, 다음 포트 0). 실제 진행은 그 토큰의 처리 차례에 한다 |
| I5 | 합류 대기열 | 노드·포트별 FIFO. 도착한 포트의 반대쪽 대기열 맨 앞 토큰이 흡수한다 |
| I6 | 분기의 대상 | 원점이 캐릭터이면 그 틱의 플레이어 위치, 지점이면 그 좌표에서 가장 가까운 생존 적. 거리 비교만 쓴다 |
| I7 | 부채꼴 자리 | 자리 i(0부터)의 각도 = 기준 방향 + (−(M−1)/2 + i) × 간격. 간격은 10°이고, (M−1) × 10°가 90°를 넘으면 90°/M로 균등 분할한다. 요청 순서대로 앞자리부터 배정한다 |
| I8 | 캐릭터 원점의 발사 위치·방향 | 7번 시점의 플레이어 위치. 방향은 시전 노드의 조준 모드로 그때 계산한다. 커서 방향은 앱이 넘기는 조준 입력(미션·도크 포인터의 월드 좌표)을 쓴다 |
| I9 | 충돌 판정 | 이번 틱 이동 선분과 적 원의 거리 ≤ 투사체 반경 + 적 반경. 출발점에서 가장 가까운 적 하나만 맞는다. 벽은 `MissionMap.CanOccupy`, 사거리는 누적 이동 거리로 판정한다 |
| I10 | 더미의 무한 체력 | `IsDummy`인 적은 `Hurt`가 체력을 줄이지 않는다. 피해 숫자는 표시한다. 경감은 0이다 |
| I11 | 노드 실행 기록 | 지불에 성공한 도착마다 기존 `NodeExecutionEvent`를 남긴다. 텔레메트리와 하이라이트가 그대로 동작한다 |

## 4. 시각화 계획

규칙 10절의 최소 오버레이에 더해, 편집 화면에서 만든 마법이 **어떻게 흐르는지 실시간으로 보이게** 한다. 표시는 모두 읽기 전용이며 규칙 계산에 영향을 주지 않는다.

### 4.1 런타임이 내보내는 읽기 모델 (Core)

| 공개 값 | 쓰임 |
|---|---|
| `Tokens` (읽기 전용 목록) | 현재 노드, 다음 포트, 남은 대기 시간, 마나, 위력, 개수, 세대, 시전 id, 합류 대기 여부와 대기 시간 |
| `NodeFeedback[노드 색인]` | 마지막 지불 비용과 그 틱 |
| `EndEvents` | 소멸 위치·사유·필요/보유 값. 표시 시간(설정 1초)이 지나면 정리한다(기존 `TrimFeedback` 방식) |
| `LastCastResult`, 틱 | HUD의 '마나 부족'·'과부하' |
| `Projectiles` | 경기장 그리기 |
| `SpellProgram` | 노드 색인 ↔ 노드 ID, 도달 가능 여부 |

UI는 이 값을 매 프레임 읽어 메시를 다시 만든다. 기존 `RuneArenaGraphic`과 같은 방식이다.

### 4.2 공용 배치 (`UI/GraphLayout.cs`)

`RuneGraphCanvas`의 `NodeRect`, `PortPosition`, `CountPorts`, `PortAt`을 정적 도우미로 옮긴다. 포트를 **방향과 번호로** 찾게 바꿔 현재의 ID만으로 찾는 문제도 없앤다. 편집 캔버스와 전투 오버레이가 같은 배치를 쓰고, 화면 변환(팬·줌 또는 축소 맞춤)만 다르게 넘긴다.

### 4.3 흐름 그리기 (`UI/SpellFlowPainter.cs`)

두 화면이 함께 쓰는 정적 그리기 함수다.

| 요소 | 그리는 방법 |
|---|---|
| 토큰 위치 | 머무는 동안에는 **나갈 엣지를 따라 이동하는 점**으로 그린다. 진행률 = 1 − 남은 대기 ÷ 노드 머무는 시간. 나갈 엣지가 없으면 노드 중앙에 그린다. 합류 대기 중이면 해당 입력 포트에 시계형 링을 그린다 |
| 토큰 색 | 세대 0은 청록, 적중 세대가 늘수록 주황 쪽으로 바꾼다. 같은 시전 id끼리는 같은 계열 색을 쓴다 |
| 노드별 토큰 수 | 1개면 점, 2개 이상이면 `×N` 배지(규칙 10절) |
| 마지막 지불 비용 | 노드 아래 `−3.0`. 지불 직후 0.3초 동안 밝게 표시한다 |
| 소멸 | 지불 불가는 붉은 테두리 깜빡임과 `필요 X / 보유 Y`, 수명 초과는 회색 깜빡임. 약 1초 유지한다 |
| 숫자 | 소수 첫째 자리까지 표시한다. 내부 값은 반올림하지 않는다 |

### 4.4 편집 화면의 실시간 흐름

- 시험 도크의 `SpellRuntime` 상태를 `RuneGraphCanvas` 위에 겹쳐 그린다. 도크에서 시전하면 편집 중인 그래프 위로 토큰이 지나가는 것이 보인다.
- 정적 표시: 도달 불가 노드는 회색, 투사체 경고는 인스펙터에 표시, 노드마다 비용 공식 문구를 보여 준다(규칙 9절).
- 노드에 마우스를 올리면 그 노드에 있는 토큰들의 마나·위력·개수·세대를 툴팁으로 보여 준다.
- 그래프를 바꾸면 도크 실행 상태가 지워지므로(D5) 오래된 토큰이 사라진 노드를 가리키는 일이 없다.

### 4.5 전투 오버레이 (`UI/RuneGraphOverlay.cs`)

- 미션 화면 오른쪽 위에 작은 패널(약 360×220)로 띄우고 `G`(D7)로 켜고 끈다. 상태는 세션 동안만 유지한다.
- 그래프 전체가 들어가게 축소 배치한다(기존 `FitGraph` 계산 재사용). 노드 라벨은 생략하고 4.3의 요소만 그린다.
- HUD: 기존 EN 게이지를 마나풀 게이지로 바꾸고, 쿨다운·비용 문구를 적재량과 시전 실패 문구('마나 부족'·'과부하')로 바꾼다.

### 4.6 경기장

`RuneArenaGraphic`은 `SpellEntities` 대신 `Projectiles`를 그린다. 운반 마나가 0보다 큰 투사체(종착 발현, 적중하면 토큰이 생김)는 밝은 테두리로 구분한다. 세대 색은 4.3과 맞춘다.

## 6. 서브 에이전트 활용

### 6.1 역할

| 역할 | 담당 | 하지 않는 것 |
|---|---|---|
| 메인 에이전트 (Opus 5.5) | 결정 관리, 작업 단위 명세 작성, 서브 에이전트 호출, 결과 검토, 빌드 확인, 단계 통합, 문서 갱신, 사용자 보고 | 대량 반복 수정(서브 에이전트에 맡긴다) |
| `rune-graph-coder` (Haiku 5.5, high) | 명세 하나를 받아 지정 파일만 수정하고, dotnet 빌드로 확인한 뒤 보고 | 설계 결정, 범위 확장, Git, 테스트 코드, 지정하지 않은 파일 수정 |

### 6.2 시작 전: 에이전트 정의 갱신 (U0.1, M)

현재 `.claude/agents/rune-graph-coder.md`는 **옛 컴파일 모델의 불변식**(E/W 코드, `Signature` 형식, Ordinal 실행 순서, 비용 공식 보존)을 지키라고 지시한다. 이번 리팩토링과 충돌하므로 1단계 전에 고친다.

- 2절 시스템 지도: 옛 구조는 "제거 대상"으로 표시하고, 새 구조(3절)와 이 계획서·규칙 문서의 경로를 추가한다.
- 3절 불변식 교체:
  - 규칙 7.3 표 전체
  - 직렬화 필드 이름·타입 유지(3.2)
  - 결정성(생성 순서 처리, FIFO 합류, 사전 순회 순서에 의존 금지, `UnityEngine.Random` 금지)
  - 시뮬레이션 틱 안에서 LINQ 쓰지 않기
  - 3.7 구현 해석 준수
- 명세에 "규칙 문서 몇 절"을 적으면 그 절을 직접 읽고 따르게 한다.
- 새 `.cs` 파일 처리: 6.5의 csproj 절차를 따른다고 적는다.

### 6.3 작업 단위 명세 양식

메인 에이전트는 서브 에이전트를 호출할 때 아래 양식을 그대로 채운다. Haiku가 해석할 여지를 줄이는 것이 목적이다.

```
[작업 단위] U2.2 시전과 토큰 처리
[목표] 한 문장
[규칙 근거] 규칙 4.1, 4.3, 4.4, 5.2 / 계획서 3.5, 3.7의 I1~I6
[수정 허용 파일] Assets/RuneCode/Core/Simulation/SpellRuntime.cs (새 파일)
[읽기 전용 참고 파일] SpellRuntimeTypes.cs, SpellProgram.cs, SpellNodes.cs, BalanceData.cs
[수정 금지] 그 밖의 모든 파일
[공개 API 계약] 메서드 시그니처를 그대로 적는다
[의사코드] 복잡한 단위는 규칙의 의사코드를 이 프로젝트 타입 이름으로 옮겨 적는다
[완료 기준] 1) 두 어셈블리 빌드 오류 0  2) 아래 손 계산 시나리오의 각 단계 값이 코드 경로상 맞음 (예: V2, V3, V8)
[보고] 에이전트 정의 6절 형식
```

### 6.4 진행 방식

1. **순차 기본**: 5절 표의 선행 관계를 따라 하나씩 호출한다. 앞 단위의 검토가 끝나야 다음 단위를 호출한다.
2. **병렬은 제한적으로**: 수정 파일이 전혀 겹치지 않고 선행 단위가 모두 끝난 경우에만 최대 2개를 동시에 실행한다(예: U2.2와 U2.4, U4.4와 U4.5). Git을 쓸 수 없으므로 worktree 격리는 쓰지 않는다.
3. **검토**: 단위가 끝날 때마다 메인 에이전트가 아래를 확인한다.
   - 수정된 파일을 직접 읽어 명세와 대조
   - 허용 밖 파일이 바뀌지 않았는지
   - AGENTS.md 규칙(주석·접근 제한자·using 순서·이름)
   - 두 어셈블리 빌드
4. **정밀 검토 대상**(U1.4, U2.2, U2.3, U3.1): 메인 에이전트가 규칙 12절 시나리오를 코드 경로를 따라 손으로 계산한다. 값이 하나라도 다르면 같은 에이전트에게 `SendMessage`로 차이와 기대값을 보내 고치게 한다.
5. **재작업 한도**: 같은 단위에서 두 번 고쳐도 맞지 않으면 메인 에이전트가 직접 고치고 원인을 진행 기록에 남긴다.
6. **충돌 보고 처리**: 서브 에이전트가 명세와 규칙의 충돌을 보고하면 메인 에이전트가 3.7 해석이나 0단계 결정으로 정한다. 결정할 수 없으면 사용자에게 그 지점만 질문한다.
7. **진행 기록**: 단계가 끝날 때마다 `docs/PROGRESS.md`에 끝난 단위, 빌드 결과, 남은 문제를 적는다. 긴 작업이라 AGENTS.md 12절에 따라 기존 기록을 갱신한다.

### 6.5 빌드 확인 방법과 제약

- 명령: 저장소 루트에서 `dotnet build RuneCode.Core.csproj`와 `dotnet build Assembly-CSharp.csproj`. 오류 0, 기준 경고(Core 2, Assembly-CSharp 4, MSB3277) 외의 새 경고가 없어야 한다.
- **csproj는 Unity가 생성하며 파일을 하나씩 명시한다.** 새 `.cs` 파일은 Unity가 csproj를 다시 만들기 전까지 빌드에 들어가지 않는다.
  - 새 파일을 만드는 단위(U1.3, U1.4, U2.1, U2.2, U4.1, U4.2, U4.4)가 끝나면, 메인 에이전트가 사용자에게 Unity Editor 포커스(자동 Refresh)를 요청하거나 csproj에 `Compile Include` 줄이 생겼는지 확인한 뒤 빌드한다.
  - 사용자가 Editor를 켤 수 없으면 메인 에이전트가 gitignore 대상인 csproj에 임시 `Compile Include`를 추가할 수 있다. Unity가 다시 생성하면 덮어쓰므로 저장소에 영향은 없다.
- dotnet 빌드 성공은 Unity 컴파일 성공이나 Play 동작 확인이 아니다. 보고할 때 구분한다.

## 8. 검증 계획

AGENTS.md에 따라 테스트 코드와 테스트 자산을 만들지 않는다. 검증은 빌드, 코드 경로 손 계산, Unity Editor 실제 조작으로 한다.

### 8.1 정적 확인 (메인 에이전트)

- 두 어셈블리 dotnet 빌드
- 옛 타입(`CompiledSpell`, `SpellAction`, `GraphCompiler`, `RuneCatalog`, `AdaptationNet`) 참조가 남지 않았는지 Grep
- 규칙 12절 V1~V9를 코드 경로로 손 계산(2단계 끝, 3단계 끝)
- 규칙 7.3의 각 항목이 어느 코드 줄에서 보장되는지 표로 정리해 PROGRESS에 남김

### 8.2 Editor 확인 (사용자, 체크리스트)

편집 화면에서 그래프를 만들고 도크에서 시전한다. 오버레이에 보이는 비용·마나·위력으로 결과를 읽는다. 4절의 시각화가 곧 검증 도구다.

- CLI `--sim`을 같은 시드로 두 번 실행해 `StateHash`가 같은지 확인한다. 옛 해시값과는 비교하지 않는다(모델이 바뀌었으므로).
